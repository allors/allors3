> **Status: Current.**

This page explains how the .NET and TypeScript workspaces complete a load and retain an editing
baseline. Each accepted database record holds both data and the security state used for its
permission checks. This is a maintainer explanation; applications must not rely on this
internals page. The tests below are authoritative. The platform boundary is in
[ARCHITECTURE.md](../../../../../ARCHITECTURE.md); domain terminology is in [Domains](../domains.md).

## Ownership

| Owner | State and responsibility |
| --- | --- |
| `DatabaseConnection` | Shares immutable database records, versioned grant/revocation contents and permission definitions between sessions. Records are cached by object ID, data version and the complete security binding: grant/revocation IDs and their versions. There is no lookup by object ID alone. |
| Load response context | Retains the exact cache entries advertised for this operation, validates the completing response, and supplies its records for session adoption. Another session's refresh cannot substitute a different record for an advertised entry. |
| `DatabaseOriginState` for a session object | Retains the last accepted database record, including its security state. `OnPulled` receives the completed load's record, checks `CanMerge`, and replaces the session record only when accepted. A merge error leaves this object's entire previous record in place. |
| `RecordBasedOriginState` | Holds local role changes separately. A to-many change is the set of objects added to and the IDs removed from the retained record's role, so adding or removing one member needs only that member in the session. Reads prefer the local value; otherwise they use the retained record. Role IDs are readable without the objects; reading the objects requires every member to be in the session. `Diff` compares local changes with that record and carries IDs, with objects for the members the session holds. `Reset` clears local changes without fetching or accepting a newer record. |
| Remote `DatabaseOriginState` | Builds Push using the retained version. To-many changes are sent as their stored additions and removals. |

## Completing a load

Whichever response completes a load determines its results. Pull supplies named objects,
collections and values, together with a pool of object versions and security bindings.

1. If the connection already holds every complete record and its exact security state, Pull
   completes the load from those retained entries. No Sync is needed.
2. Otherwise, Sync receives the original Pull request, including its arguments and dependencies,
   and descriptions of the complete records and security entries the client can reuse. The
   server re-executes that request. Sync's named results and complete object pool replace the
   first Pull's selection; they are not additions to it.
3. The client validates all selected records, security contents and permission definitions before
   publishing cache entries or adopting session records. Missing, inconsistent or malformed
   contents fail the load without partially publishing that response.

Sync evaluates its selection, object contents and security using the same transaction and
access-control instance. The SQL snapshot regression
`SelectionContentsAndSecurityUseTheSameSnapshot` in
[the server Sync tests](../../../../../dotnet/Core/Database/Server.Local.Tests/Json/Sync/SyncObjectTests.cs)
checks this when another transaction commits data and security changes during Sync.

The cache reuse rules distinguish missing contents from complete empty contents:

| Sync contents | Meaning |
| --- | --- |
| Omitted or null object role table | Reuse the exact complete record advertised by this operation, including its security binding. Matching the data version alone is insufficient. |
| Omitted or null grant/revocation permission list | Reuse the exact advertised entry for that ID and version. |
| Empty role table or permission list | Complete contents with no entries. This is not a request to reuse cached contents. |

A security change can therefore require Sync and fresh object contents even when the data
version is unchanged. Normal loads obtain security contents and permission definitions in
Sync; they no longer make separate Access or Permission requests. Those transport methods
remain available. The revised protocol requires matching client and server versions; it has
no compatibility bridge to the previous protocol.

Named collections preserve their order and repeated objects. An object absent from the final
selection is absent from that result; its absence does not delete an existing session object.
A session holds only the objects its own loads returned. Navigating a role to an object the session
does not hold, or instantiating one by ID, fails with an error that names the object.
Versioned entries remain in memory for the connection's lifetime; eviction and persistence
are not implemented.

The [shared .NET Pull tests](../../../../../dotnet/Core/Workspace/Tests/Tests/PullTests.cs) cover
`PullUsesFinalSelectionAndCompletesExactCacheHits`,
`PullRetainsAdvertisedRecordsAcrossOverlappingSessions`,
`PullFinalAbsencePreservesExistingSessionObjects` and
`PullRejectsIncompleteResponsesAtomically`. The corresponding TypeScript coverage is in
[the Pull result specs](../../../../../typescript/modules/libs/system/workspace/adapters-json-tests/src/lib/database/pull/pull-result.spec.ts)
and [response context specs](../../../../../typescript/modules/libs/system/workspace/adapters-json-tests/src/lib/database/security/response-context.spec.ts).

These guarantees cover overlapping loads in distinct sessions sharing a connection. They do
not establish concurrent use of one session. After a valid load, merge acceptance remains
per object: one object can retain an older record after a merge error while another accepts
the new record. Local edits and objects retained from earlier loads also remain in the session.
The resulting session is therefore not a snapshot of the whole object graph.

## Characterization matrix

The tests use two sessions of one workspace/connection. A remote session changes and pushes an
object, then pulls it to refresh the shared connection. The editing session has local changes
to a string, a many-to-one role, and a many-to-many role. All relation targets are loaded.

| Case | Observed behaviour | Authoritative tests |
| --- | --- | --- |
| Only the remote session pulls | The editing session keeps its version, untouched integer value, local values, and all three diff originals. Its Push reports a version error (.NET returns a result; TypeScript throws `ResultError` with that result). Reset returns to the old baseline; a subsequent Pull accepts the remote record. | `DatabaseDiffRetainsBaselineWhenAnotherSessionRefreshes` / `databaseDiffRetainsBaselineWhenAnotherSessionRefreshes` |
| Remote changes only the integer | Editing Pull accepts the newer version and integer while preserving all three local edits and their diff originals. A subsequent Push succeeds and preserves both sides' changes. | `DatabaseEditingBaselineAfterPull("disjoint")` / `databaseEditingBaselineAfterPull: disjoint` |
| Remote changes one locally edited role plus the integer | Editing Pull reports one merge error for the object. Its version, integer, all local edits, and all diff originals remain unchanged. Reset clears edits but keeps the old record; Pull then accepts the remote record. | The `string`, `to-one`, and `to-many` rows of the same tests |

The to-many conflict deliberately uses additions of different members. Merge compares the whole
role against its baseline; it does not combine independent membership changes within that role.
The representative relation cases do not establish every cardinality or inverse-association
behaviour.

## Unit merge equality

Merge compares the retained baseline with the refreshed remote value for each locally edited
role. It compares DateTime and binary values by content in both runtimes; the local value does
not decide whether the remote baseline changed.

| Locally edited role | .NET (both HTTP adapters) | TypeScript HTTP |
| --- | --- | --- |
| DateTime | `Equals` compares DateTime values. | Date timestamps are compared with `getTime()`. |
| Binary | `SequenceEqual` compares byte-array contents, including length. | Binary is a base64 string, compared by value. |

`DatabaseUnitEqualityDuringDisjointPull` / `databaseUnitEqualityDuringDisjointPull` start with a
non-null unit value, edit it locally, and change only an integer remotely. Pull accepts the new
record/version while preserving the local edit and its diff original. A newly decoded array or
Date instance representing the same value does not cause a conflict.

`DatabaseUnitValueEqualityDuringPull` / `databaseUnitValueEqualityDuringPull` cover both units
with an unchanged null baseline, null-to-value and value-to-null transitions, different remote
values, and local removal with an unchanged remote value. Binary also covers a length change
with the same starting bytes. Equal baselines accept the refreshed record; actual changes report
a conflict and retain the old record/local edit until Reset followed by Pull. Null remains
distinct from a non-null value. Other unit types and relation comparisons keep their existing
rules. Binary comparison can scan the byte contents; DateTime comparison is constant-time.

## Push does not accept a new baseline

A successful Push marks the session object's database state as pushed. It does not accept a new
baseline. When a later completed load includes the object, it clears the pushed local changes
and accepts that load's record without the ordinary merge check. The existing
`ResetUnitAfterPushTest` and `resetUnitAfterPush` tests remain unchanged: Reset after Push,
without Pull, exposes the last pulled value.

## Retained permissions

`DatabaseRecord.IsPermitted` / `isPermitted` uses the immutable grant and revocation contents
retained by that record. Refreshing the shared connection from another session changes neither
the editing session's data baseline nor its permission checks. The implementation is in
[the .NET database record](../../../../../dotnet/System/Workspace/Adapters/Allors.Workspace.Adapters.Remote/Database/DatabaseRecord.cs)
and [the TypeScript database record](../../../../../typescript/modules/libs/system/workspace/adapters-json/src/lib/database/database-record.ts).

`PullRequiresContentsWhenOnlySecurityChanges` in the shared .NET Pull tests checks both sides:
the loading session adopts changed permissions and contents even without a data-version
change, while the other session retains its earlier
readable value and permission. The TypeScript response context specs check that changed
security requires fresh contents even with a cached object. The existing
`RefreshesKnownGrantWhenAnObjectIsSynchronized` and
`RefreshesKnownRevocationWhenAnObjectIsSynchronized` tests in
[the shared .NET security tests](../../../../../dotnet/Core/Workspace/Tests/Tests/SecurityTests.cs)
and [TypeScript security specs](../../../../../typescript/modules/libs/system/workspace/adapters-json-tests/src/lib/runtime/security.spec.ts)
also cover permission changes on a synchronized object.

Adopting a record updates its data and security together. A merge conflict retains both from
the old record, along with the local edits. Reset clears those edits but keeps that record;
a subsequent Pull can accept the new one. The guided permissions scenario illustrates these
combined rules. Its table shows held values separately from permission to expose them.

This is a retained authorization snapshot, not a guarantee of the server's latest permissions.
Server changes take effect in the session when it accepts a completed load's record. Push is
still authorized by the server: `RejectedExistingObjectPushReturnsAccessErrorAndRollsBack` in
the shared security tests checks that a server-side permission removal rejects an existing
object's Push even though the client retained permission to edit it.

## Open decisions

- Decide whether failed Push should keep returning an error result in .NET and throwing
  `ResultError` in TypeScript. The baseline tests now pin both surfaces; aligning them would be
  an API behaviour change for callers and needs separate approval.
- Decide whether to preserve the current baseline transitions in the connection/session split,
  including Reset after Push and whole-role conflict detection. The matrix is evidence for that
  decision, not approval to change semantics or to combine to-many membership edits.
- Any automatic refresh or invalidation policy must account for retained data and security,
  including records kept after a merge conflict. The current load contract does not itself
  schedule refreshes or update idle sessions.

The connection/session split, Push error-contract changes, cache eviction or persistence, and
signals remain separate work. The final-selection protocol and shared versioned caches described
above are implemented.
