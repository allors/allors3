> **Status: Current.** Explanation for maintainers of the .NET and TypeScript remote workspaces.

A session object keeps its data and security together. While it has pending database-role
edits, Pull leaves its active snapshot in place and records the latest complete snapshot
received by that session. Reset clears those edits and adopts the latest received snapshot
without another request. Applications can preserve chosen edits before Reset and reapply them
against the adopted snapshot.

Here, edits mean changes to database-origin roles, including changes to roles that the server
has not changed. Session-origin values keep their existing, separate lifecycle. The platform
boundary is in [ARCHITECTURE.md](../../../../../ARCHITECTURE.md); relation terminology is in
[Domains](../domains.md) and [Terminology](../terminology.md).

## Ownership

| Owner | State and responsibility |
| --- | --- |
| `DatabaseConnection` | Shares complete cached payloads and exact grant/revocation versions. Publishing another version does not modify retained entries. |
| Loading workflow | Selects complete cache entries, obtains missing data and security through Sync, and validates the result before publication or session adoption. |
| Session object | Retains an active snapshot and the latest complete snapshot received by its own successful loading workflow, including cache hits. |
| `DatabaseOriginState` | Reads and diffs against the active snapshot, stores database-role edits separately, and uses the active data version for Push. Reset clears edits and adopts the latest received snapshot. |

A snapshot contains an object data record and its exact grant/revocation bindings. The same
object data version can have different readable values under different security versions.
The [hybrid Sync explanation](workspace-hybrid-sync.md) describes the wire contract and cache
ownership. The rules here are per object; they do not establish snapshot consistency across
an entire object graph.

## Pull and Reset

| Event | Result |
| --- | --- |
| This session loads an unedited object | Adopt the received data and security together. |
| This session loads an edited object | Keep its active data, security, edits and diff originals. Record the received snapshot as the latest. No automatic merge occurs. |
| This session loads another complete snapshot before Reset | Replace its latest received snapshot; keep the active snapshot pinned. |
| Another session loads the object | Neither this object's active snapshot nor its Reset target changes. |
| Reset | Clear edits and adopt this session's latest received snapshot. No Pull or Sync is needed. |
| Loading or validation fails | Preserve the session's snapshots and edits. |

A change to an untouched integer does not advance an object with a locally edited string.
The rule is the same for strings, units, to-one roles and to-many roles. After Reset, an
application may reapply selected changes after checking the adopted snapshot's permissions.
Those changes become ordinary edits with new diff originals. To-many changes are not combined
automatically.

If only another session has loaded a newer snapshot, Reset still uses this session's previous
snapshot. A later Pull is needed to receive something newer in that case. Reset never selects
an arbitrary latest entry from the shared connection.

## Behavioural coverage

The existing editing-baseline matrix covers a remote integer change and overlapping string,
to-one and to-many changes. Each editing Pull retains the active snapshot; Reset adopts the
latest received one. DateTime and binary cases follow the same rule regardless of whether the
remote value equals the original value. Diff originals continue to describe the active
snapshot until Reset clears the edits.

The cross-session diff cases verify that another session's Pull does not change the editing
baseline or Reset target. Push with an old data version can still fail: .NET returns an error
result, while TypeScript throws `ResultError` containing that result. That API difference is
unchanged.

## Push and authorization

A successful Push marks the database state as pushed; it does not fetch a new snapshot.
The next successful Pull that includes the object clears those already-committed edits and
adopts its received snapshot.
Reset after Push, with no newer snapshot received, exposes the previous pulled value. This does
not undo the database Push. The existing `ResetUnitAfterPushTest` and `resetUnitAfterPush` cases
cover that sequence.

An active snapshot retains the grant/revocation versions used to filter its data. Refreshing
another cache entry does not change its read, write or execute permission description. Reset
adopts the received permissions with their matching data, including values that have become
readable or are no longer readable.

Cached descriptions do not authorize server operations. Push and Invoke continue to apply
their server authorization and version checks. Signals, persistent caching and alignment of
the two Push error APIs remain separate work.
