Recommendation
Use the existing shared test source directory dotnet/Core/Workspace/Tests/Remote for one copy of
the HTTP PullTests and one small standalone pure ReadTransportTests. Both existing remote test
projects compile these linked files; the existing Tests project excludes exactly these two files
from its compile. No new test project and no production source/API/friend-assembly change.

Each remote csproj supplies two namespace aliases through SDK Using items:
- RemoteAdapter -> Allors.Workspace.Adapters.Remote.SystemText or .Newtonsoft.
- RemoteCodec -> Allors.Protocol.Json.SystemTextJson or .Newtonsoft.
Qualify the existing concrete DatabaseConnection/ReadTransport/PushReadTransport/InvokeReadTransport
references with RemoteAdapter and existing ReadJson/PushReadJson/InvokeReadJson/UnitConvert
references with RemoteCodec. Avoid chained aliases and runtime bool/reflection dispatch. The aliases
remain compile-time names for the actual concrete implementations, not a replacement transport.
The shared test files remain in namespace Tests.Workspace.Remote. No namespace-alias collision was
found in the current remote project sources. Using items generate ordinary SDK global usings during
a build; no generated file is edited by hand. Compiler validation remains future work.

Costs and alternative
The proposal trades one duplicated 1,475-line source file for two explicit linked Compile entries
and two aliases in each codec project, and two Compile exclusions in the existing shared project.
This neutral shared location is clearer than making Newtonsoft own a linked SystemText test file.
An abstract class compiled in Workspace.Tests would require moving/changing codec-specific Profile
and HttpTestResources or introducing a larger factory abstraction, both outside the small duplication
problem. Conditional imports are feasible, but need a codec build symbol and error handling for
missing/wrong symbols in both files; two explicit namespace aliases keep the dependency choice
visible in the consuming project without extra test control flow.

Why fixture removal is necessary
Current PullTests : Workspace.PullTests inherits Test : IAsyncLifetime. Its constructor creates
new Profile(); Test.InitializeAsync calls Profile.InitializeAsync(), which GETs
Test/Setup?population=full and then Login("administrator") (real connection bootstrap). Thus all
seven otherwise pure rows currently perform real host/database setup. A trait/filter alone does
not remove that initialization. Fixture itself only builds database metadata/rules, but the base
lifecycle and Profile are the live dependency. A standalone class removes both costs and dependency.
